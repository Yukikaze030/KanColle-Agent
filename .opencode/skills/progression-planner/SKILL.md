# 练舰规划

遵循已加载的 `kancolle-main` 公共约束；若未加载，先加载。

## 查询顺序

1. 先用 Poi 的舰娘查询取得 `master_id/name/level/locked/condition/repair`，用库存查询取得改造道具与基础资源。结果很多时先按舰种、等级区间或候选名过滤，不索取整份账号数据。
2. **本地优先**：先读 `refs/INDEX.md`，再按需求读取对应本地 Markdown。基础练级读 `training-policy.md`；图纸等稀缺改造投资读 `blueprint-policy.md`；解释定位或解决同级候选才读 `ship-perf-nga.md`。不要一次加载全部参考，也不要在本地已有答案时重复访问网页。
3. 仅当本地索引没有候选、来源版本落后于问题涉及的实装时间，或涉及当前活动/当前掉落等时效信息时，才委派 researcher 在线补查。仍无价值证据时只能列“待核实候选”，不得仅因等级已够或成本较低把它排第一。
4. 结合已有高等级舰找功能缺口，避免重复建设。先列候选，再查询候选的静态数据，不对全图鉴逐舰调用 Data。
5. 对每艘拟推荐改造的船用当前形态 ID 调用 `kc_ship_remodel`，核实目标形态及等级；需要跨多次改造规划才取 `scope=family`。优先考虑接近下一改且有价值的候选；无下一改则只设当前形态练级或已核实活动需求。
6. 改造建议必须核对目标的完整消耗，再用 `poi_get_inventory` 对照持有量及 coverage。以 `transitions` 的有向转换及消耗为准；`partial/missing` 不等于免费。Data 缺消耗或道具定义才委派 researcher 定向补查。
7. 资材用 `kc_search(types=["item"])` / `kc_get(item:ID)` 按需核实身份，再按 ID 对照 `useitems.master_id/name/count`；equipment 消耗查装备库存，resources 对照基础资源，不能混用或拿相似道具数量代替。翻译/别名关系无证据时保留原名并待核实，不猜航空/火炮二选一。
8. 按排序累计扣除共用资源，区分「现在可改」「先练级、待资源」「待核实」。已知一项不足可判暂不能改，但消耗未全时不得声称唯一瓶颈或排序不受影响。
9. 输出优先级、当前 → 目标等级、理由及相关资源的需求/持有/缺口；大破/入渠舰不作近期练级首选。影响可行性的缺项在本次任务内补查；仍不可得则列明，不能以“可另查”代替核实。

## 排序规则

按以下顺序做决定，而不是只按最终强度或离改造等级最近排序：

1. **解除硬缺口**：当前账号没有可稳定承担的必要功能或近期任务指定舰。
2. **形成基础轮换**：常用舰种、联合舰队位置、支援与远征需要的第二套可用成员。
3. **高频泛用提升**：多个常规海域和任务都能复用，且升级后立即产生收益。
4. **稀缺道具效率**：只在功能收益相近且已有来源支持时比较成本；完整改造成本更低、不会挤占更高优先候选者靠前。
5. **专用与重复建设**：仅单一场景、重复功能、收藏或豪华二号机通常后置。

将“值得练到改造等级”和“现在值得消耗图纸/详报等完成改造”分成两个结论。排序时按顺序累计扣除共享道具；后位候选不得重复使用已经分配给前位候选的资源。

## 输出格式

最多给 3 个主推荐，并设“现在 / 接下来 / 暂缓”三档。每项包含：`当前形态与等级 → 已核实目标及等级`、补足的账号功能、练级理由、完整消耗与持有/缺口、立即行动。候选资料或当前需求无法核实时写明置信度，不用模糊信息硬排。

附属查阅：`refs/SOURCES.md` 与按主题拆分的 refs。舰娘性能/改造以 Data MCP 为准；社区资料只用于价值判断。改造是否存在与消耗仍以 Data `kc_ship_remodel` 为准，refs 不得写未核实改二。
